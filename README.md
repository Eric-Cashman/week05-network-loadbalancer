# Week 5: Multi-Subnet Network Topology & Load Balancer

A Docker Compose project that puts an Nginx load balancer in front of two Node.js backends, split across a public and a private subnet. The first draft was generated by an AI assistant, then audited, tested, and patched by me.

## Architecture Overview

```
                 Host / Internet
                        |
                   port 80 (HTTP)
                        |
   public_subnet  10.10.1.0/24
                        |
              +--------------------+
              |    loadbalancer    |   Nginx 1.27, round-robin
              |    (dual-homed)    |
              +--------------------+
                        |
   private_subnet  10.10.2.0/24   (internal: true, no host ports)
              |                    |
      +-------------+      +-------------+
      |  backend1   |      |  backend2   |   Node.js 22, port 3000
      +-------------+      +-------------+   (expose only, never published)
```

- **public_subnet (10.10.1.0/24):** reachable from the host. Only the load balancer is on it.
- **private_subnet (10.10.2.0/24):** marked `internal: true`. The backends live here and publish no ports.
- **loadbalancer:** the only service on both networks. It publishes port 80 and distributes requests round-robin.
- **backend1 / backend2:** each returns its own hostname in the JSON body and in an `X-Served-By` header, and serves `/healthz`. Each has a Docker `HEALTHCHECK`.

## Setup & Execution Guide

**Requirements:** Docker Desktop (Docker Compose v2).

1. **Clone the repository:**
   ```
   git clone https://github.com/Eric-Cashman/week05-network-loadbalancer.git
   cd week05-network-loadbalancer
   ```
2. **Build and start everything:**
   ```
   docker compose up --build -d
   ```
3. **Check the containers** (backends show "healthy" after about 10 to 30 seconds):
   ```
   docker compose ps
   ```
4. **Send 10 requests** and see which backend answered each one (PowerShell):
   ```
   1..10 | ForEach-Object { (curl.exe -s http://localhost/ | ConvertFrom-Json).server }
   ```
5. **Check the health endpoint through the load balancer:**
   ```
   curl.exe -i http://localhost/healthz
   ```
6. **Stop** (keeps containers): `docker compose stop`
7. **Clean up** (removes containers, networks, and built images): `docker compose down --rmi local`

If port 80 is already in use on your machine, change `"80:80"` in `docker-compose.yml` to another port such as `"8080:80"`.

### Audit against the Network Reality Check

| Check | Result |
|---|---|
| Port leakage and isolation | **Good.** Backends use `expose`, not `ports`. `docker compose ps` shows no host mapping, and `docker port backend2` prints nothing. The private network is also `internal: true`. |
| Subnet dual-homing | **Good.** `docker inspect` shows the load balancer on both networks and each backend on `private_subnet` only. |
| Upstream configuration and DNS | **Good, with one omission.** It uses Docker service names (`backend1:3000`), not hard-coded IPs. It had **no** connection timeouts and **no** `proxy_next_upstream` retry settings. |
| Session persistence vs. balancing | **Good.** Default round-robin, stateless backends, no sticky sessions. Ten requests alternated `backend1`, `backend2`. |

### What the AI got right
- Backends are never published to the host and sit on an `internal` private network.
- Only the load balancer is dual-homed.
- Service-name discovery instead of static IPs.
- Each backend returns its hostname in the body and an `X-Served-By` header, and has `/healthz` plus a Docker `HEALTHCHECK`.

### What I found and patched
1. **Slow failover (missing timeout and retry settings).** With `backend1` stopped, the first request still returned `200`, but took **14.3 s**, and later a stalled request took **3.1 s** about every 10 seconds. The nginx log showed `connect() failed (113: Host is unreachable)`: nginx was waiting on the dead backend before trying the healthy one. I added `proxy_connect_timeout 1s`, `proxy_next_upstream error timeout http_502 http_503 http_504`, `proxy_next_upstream_tries 2`, `proxy_next_upstream_timeout 5s`, and `fail_timeout=30s` on each backend. The stall dropped to about **1.0 s**. See the commit "Fix slow failover".

### Known gaps I did not fix
- Open-source nginx only detects a dead backend by trying it, so while a backend is down, one request about every 30 seconds still pays a 1-second delay. Active health checks would remove this.
- Nginx resolves backend names only at startup. On my first run it refused to start with `host not found in upstream` because the backends weren't running yet. I did not test what happens if a restarted backend gets a different IP.
- A single load balancer is a single point of failure.
- HTTP on port 80 only. There is no TLS on 443.
- The backend answers `200` for every URL, including unknown paths.
